# Harness Evolve — 실행 결과를 하네스에 반영하기

하네스는 한 번 만들고 끝나는 산출물이 아니다. 이 스킬은 실행 결과에서 효과가 있었던 것과 없었던 것을 찾아 하네스에 반영한다. 그래서 다음 실행이 눈에 띄게 나아지도록 한다.

```
처음 하네스 ──▶ 실제 프로젝트에서 사용 ──▶ 현재 하네스
                                            │
                                            ▼ (evolve로 차이 분석)
                                      피드백 정리 → 에이전트·스킬·오케스트레이터에 반영
                                            │
                                            ▼
                                      변경 이력 갱신 → 다음 실행은 더 나은 초안에서 시작
```

## 진행 절차

### 1단계: 변경 내용 수집

1. `.claude/agents/`, `.claude/skills/`, `CLAUDE.md`의 변경 이력 표를 읽는다.
2. git 저장소라면 하네스 파일의 변경 이력을 조회한다(`git log --oneline -- .claude/ CLAUDE.md`). 처음 구성과 비교해 무엇이 언제, 왜 바뀌었는지 파악한다.
3. `_workspace/`가 있으면 최근 실행의 중간 산출물을 훑어 실제로 실행된 흔적을 확인한다.
   - 오케스트레이터가 정한 경로에 산출물이 실제로 있는지 확인한다. 없으면 워크플로를 거치지 않았거나 쓰이지 않는 코드다.
   - 산출물이 스킬에 적힌 형식과 기준을 따르는지 확인한다.
4. 사용자에게 피드백을 요청한다. 사용자가 이미 피드백을 주었으면 생략한다.
   - "결과에서 개선할 부분이 있나요?"
   - "에이전트 구성이나 워크플로에 바꾸고 싶은 점이 있나요?"
   - 피드백이 없으면 강요하지 않는다. 다만 아래 신호가 보이면 먼저 개선을 제안한다.

**피드백이 없어도 개선을 제안할 신호:**

- 같은 종류의 수정 요청이 두 번 이상 나왔다.
- 에이전트가 반복해서 실패하고 다시 시도했다.
- 사용자가 오케스트레이터를 거치지 않고 직접 작업했다. 오케스트레이터의 호출 조건이 맞지 않았을 수 있으므로 `description`을 넓힐 후보다.
- 오케스트레이터에 `TeamCreate`, `TeamDelete`, 실험 기능 플래그 같은 v1 방식이 남아 있다. harness 스킬의 전환 절차를 안내한다.

### 2단계: 피드백 분류와 수정 대상 정하기

| 피드백 종류 | 수정 대상 | 예시 |
| --- | --- | --- |
| 결과물 품질 | 해당 에이전트의 스킬 | "분석이 너무 피상적" → 스킬에 분석 깊이 기준 추가 |
| 에이전트 역할 | 에이전트 정의 `.md` | "보안 검토도 필요" → harness 스킬로 에이전트를 추가하도록 안내 |
| 작업 순서 | 오케스트레이터 스킬 | "검증을 먼저 해야" → 단계 순서 변경 |
| 팀 구성 | 오케스트레이터와 에이전트 | "이 둘은 합쳐도 될 듯" → 에이전트 병합 |
| 호출 조건 누락 | 스킬 `description` | "이 표현으로 하면 작동 안 함" → `description` 확장 |
| 맞지 않는 실행 모드 | 오케스트레이터 | "매번 같은 팬아웃인데 느려" → 워크플로 조율로 전환 |
| 규모와 비용 | 오케스트레이터 | "토큰을 너무 써" → 기본 규모 축소, 토큰 예산 연동 추가 |

**처리 범위:** 에이전트를 새로 추가하거나 삭제해야 하거나 구조를 다시 설계해야 하면 이 스킬에서 직접 처리하지 않는다. harness 스킬의 0단계에 있는 기존 구성 확장 절차로 안내한다. evolve는 **기존 구성을 조정하는 일**에 집중한다.

### 3단계: 피드백 정리와 반영

1. **여러 상황에 적용할 수 있게 정리한다.** 한 사례에만 맞춘 좁은 수정은 다른 상황에서 통하지 않는다. "이번 보고서의 서론이 길었다"는 피드백에 "서론은 전체의 10% 이내로"라는 규칙을 넣지 않는다. 서론이 길어진 원인(스킬에 분량 배분 기준이 없음)을 찾아 원리 수준에서 고친다.
2. **이유를 함께 적는다.** 고친 지시에 이유를 붙인다. 이유를 알면 에이전트가 예외 상황에서도 올바르게 판단한다.
3. 변경은 한 번에 하나씩 적용하고, 변경할 때마다 곧바로 4단계를 실행한다.
4. **이전 수정을 되돌리지 않는지 확인한다.** 이번 수정이 변경 이력에 있는 이전 수정을 되돌리는 방향이면 사용자에게 충돌을 알리고 확인받는다. 예를 들어 예전에 "너무 길다"는 피드백으로 줄였는데 이번에는 "너무 짧다"는 피드백이 왔다면 두 요구를 모두 만족하는 기준을 찾는다.
5. **기존 파일의 언어를 따른다.** 에이전트·스킬·오케스트레이터·`CLAUDE.md`에 넣는 문장은 수정할 파일에 이미 쓰인 언어로 쓴다. 이 스킬 문서가 한국어로 쓰였다는 이유로 다른 언어로 된 하네스에 한국어 문장을 섞지 않는다.

### 4단계: 변경 이력 갱신과 검증

1. `CLAUDE.md`의 **변경 이력** 표에 기록한다.

```markdown
**변경 이력:**
| 날짜 | 변경 내용 | 대상 | 사유 |
|------|----------|------|------|
| 2026-07-19 | 톤 가이드 추가 | skills/content-creator | "너무 딱딱하다" 피드백 |
```

2. 고친 파일의 구조를 검증한다. 프론트매터와 참조 이름이 맞는지 확인한다.
3. `description`을 고쳤으면 호출 조건을 검증한다. 스킬을 불러와야 하는 요청과 불러오면 안 되는 경계 사례를 각각 3개 이상 만들어 확인한다.
4. 마지막으로 `CLAUDE.md`와 실제 파일이 일치하는지 확인한다.

### 5단계: 결과 보고

사용자에게 다음 내용을 보고한다.

- 처음 구성과 현재 상태의 차이 요약
- 이번에 반영한 변경과 그렇게 정리한 근거
- 반영하지 않기로 한 피드백과 그 이유(있다면)
- 다음 실행에서 기대하는 개선점

## 원칙

- **변경 이력은 자산이다.** 이력이 쌓일수록 같은 분야의 다음 하네스를 실제로 쓸 수 있는 수준에 더 가까운 초안에서 시작할 수 있다. 이력을 지우지 않는다.
- **정리하지 않은 피드백은 반영하지 않는다.** 사례 하나마다 규칙을 하나씩 추가하면 스킬이 규칙 목록으로 변한다. 원리로 줄여서 반영한다.
- **한 번에 하나씩 바꾼다.** 여러 변경을 한꺼번에 적용하면 어떤 변경이 효과가 있었는지 알 수 없다.
